# GitHub Projects Övning

Detta repo skapades som en del av en gruppövning i att organisera och samarbeta med **GitHub Projects, Milestones och Issues**.  
Syftet var att träna på att strukturera projektarbete, använda Kanban-metodik och arbeta tillsammans i GitHub.

---

## 🎯 Mål med övningen
- Skapa och organisera ett GitHub Project Board.
- Arbeta med **Milestones** för att planera leveranser.
- Skapa och hantera **Issues**.
- Samarbeta i grupp och turas om att vara repoägare, driver och navigator.

---

## 🛠️ Del 1 – Repo, Project Board & Milestones
- Vi skapade ett gemensamt repo: `github-project-<allasFörnamnPåRad>`.
- En enkel `README.md` lades till.
- Collaborators bjöds in med **Write access**.
- Ett **Project Board** sattes upp i Kanban-layout med följande kolumner:
  1. Backlog  
  2. Blocked / Waiting  
  3. Review / Code Review  
  4. Testing / QA  
  5. On Hold / Parked  
  6. Low Priority / Icebox  
  7. Done  

- Följande **Milestones** skapades:
  - `MVP` – första fungerande versionen  
  - `UI Improvements` – design och layout  
  - `Testing & QA` – testning och kvalitetssäkring  
  - `Feature Complete` – alla funktioner implementerade

---

## 🗂️ Del 2 – Issues & organisering
- Vi skapade Issues enligt en tabell, och tilldelade:
  - **Assignees** (en person ur gruppen per issue)  
  - **Labels** (standardlabels, t.ex. bug, enhancement)  
  - **Milestones** kopplade till varje issue  

- Därefter flyttades issues in i rätt kolumn på Kanban-boarden.  
- Vi tränade på att prioritera, kommentera och uppdatera status under arbetets gång.

---

## ✅ Del 3 – Stänga Issues & följa progress
Vi provade alla tre sätt att stänga issues:
1. Via **Issue-vyn** (`Close issue`).
2. Via **Milestone-vyn** (progressbar uppdaterades).
3. Via **Project Board** (dra kortet till `Done`).

👉 Vi lärde oss att för att **Milestones progressbar** ska uppdateras krävs att issue:n är stängd, inte bara flyttad på boarden.

Alla i gruppen fick:
- Testa alla tre sätten som både **driver** och **navigator**.
- Självständigt stänga minst ett issue.
- Se hur Milestones nådde **100% progress** när alla issues var stängda.

---

## 💡 Reflektion
- **Överskådlighet:** Milestone-vyn gav bäst helhetsbild av progress.  
- **Tydlighet:** Att stänga issue via Project Board kändes mest "agilt" i praktiken.  
- **Uppföljning:** Progressbaren i Milestones gör det lätt att se hur nära leverans teamet är.  

---

## 📚 Sammanfattning
Vi har tränat på ett arbetsflöde som speglar **agilt projektarbete** i GitHub.  
Alla i gruppen fick erfarenhet av att:
- Skapa repo, board, issues och milestones.  
- Organisera och flytta arbete i en Kanban-board.  
- Stänga issues på flera olika sätt.  

Resultatet är ett repo som dokumenterar ett realistiskt arbetsflöde i GitHub – värdefullt för framtida samarbetsprojekt och portfolioprojekt.
